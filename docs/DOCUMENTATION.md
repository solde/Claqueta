# Pautas de documentación

Estas son las reglas para documentar el proyecto. Se cumplen **en cada cambio** y varias las comprueba un test (`tests/docs-coverage.test.mjs`, parte de `npm test`), así que la documentación no se queda atrás sin que nadie lo note.

## 1. Principios
1. **Se documenta el porqué, no el qué.** El código ya dice lo que hace; el comentario explica la intención, la restricción, la unidad, el riesgo de seguridad o la razón de una decisión poco obvia.
2. **Cerca del código.** Lo que cambia con una función vive en un comentario de esa función; lo que cambia con una pieza vive en la cabecera de su fichero; lo que cambia con el producto, en `docs/`.
3. **Una sola fuente de verdad.** Si algo se puede **generar** a partir del código (entidades, rutas, mapa de ficheros, catálogo de memorias, iconos), se genera. Nunca se edita a mano un documento generado.
4. **La documentación se prueba.** Si una regla se puede comprobar con un test, hay un test.
5. **Quien cambia el comportamiento actualiza la documentación en el mismo cambio.**

## 2. Idiomas
| Qué | Idioma |
|---|---|
| Comentarios de código, mensajes de commit, nombres | **Inglés** |
| Documentación de `docs/`, README, pautas del agente (`app-seed/workspace/agent`) | **Castellano** |
| Textos de la interfaz | Castellano, catalán e inglés (los tres diccionarios deben tener las mismas claves) |

## 3. Qué se documenta y dónde
| Pieza | Dónde | Cómo |
|---|---|---|
| Qué es un fichero y cómo encaja | **Cabecera del fichero** | Obligatoria en todo fichero fuente (ver 4) |
| Una función, clase o constante exportada | Comentario `/** … */` justo encima | Obligatorio (ver 5) |
| Un método público de una clase | Comentario `/** … */` justo encima | Obligatorio en las clases de `gateway/lib`, `desktop/sync` y `app-seed/app/lib` |
| Una decisión no obvia, un invariante, una trampa | Comentario `//` en el punto exacto | Cuando el código por sí solo sorprendería |
| Una prueba | Cabecera del fichero + nombres de test que son frases | Ver 7 |
| El diseño, la seguridad, la operación | `docs/*.md` | Ver 8 |
| Entidades y campos | `docs/DATA-MODEL.md` | **Generado** desde `schema/*.mjs` |
| Rutas HTTP | `docs/API.md` | **Generado** desde `routes.mjs` (+ descripciones en `scripts/docs-api.mjs`) |
| Índice de ficheros | `docs/CODE-MAP.md` | **Generado** desde las cabeceras |
| Secciones de las memorias | `docs/MEMORIAS.md` | **Generado** desde `memoir-catalog.mjs` |
| Cómo trabaja el agente | `app-seed/workspace/agent/**` | Pautas y skills; siguen sus propias reglas (ver 9) |

## 4. Cabecera de fichero
Todo fichero fuente (`.mjs`, `.js`, `.cjs`, `.py`, `.sh`, `.html`, `.css`) empieza con un comentario que responde, en este orden:
1. **Qué es** (la primera frase, completa y que se entienda sola: es lo que aparece en `CODE-MAP.md`).
2. **Por qué existe o qué decisiones lo moldean** (seguridad, rendimiento, compatibilidad).
3. **Cómo se usa**, si es un script (`Usage: …`) o tiene un protocolo (formato de mensajes, de ficheros).

```js
// Atomic JSON store of users, roles, sessions and the audit log of the gateway. Everything is persisted with a temporary file and a rename,
// so a crash can never leave a half-written store; the CLI (user:create...) edits the same files from another process and the store re-reads them.
```
- Los ficheros **generados** lo dicen en la cabecera (`GENERATED by …: do not edit`) e indican el generador.
- La primera frase termina en punto y tiene sentido sin el resto (evita «Utilidades.» o «Ver abajo.»).

## 5. Comentarios de documentación (`/** … */`)
- **Una línea** siempre que se pueda; en prosa, en tercera persona y con verbo: «Creates…», «Returns…», «Throws … when…».
- Di lo que el nombre **no** dice: **unidades** (céntimos, segundos, minutos), **formato** (`YYYY-MM-DD`), **efectos** (escribe en disco, cambia el estado), **errores** (qué se lanza y con qué código), **permisos** que exige y **qué devuelve** si es una forma compuesta (`{ rows, total, refs }`).
- Los parámetros solo se describen cuando no son evidentes; no se repite el tipo.
- En una clase, un comentario sobre la clase (su papel y su invariante) y otro por cada método público; los métodos privados (`#nombre`) solo si hay algo que explicar.
- Una función interna se documenta si tiene lógica no trivial o si el motivo no es evidente.

```js
/** Day of the week of a YYYY-MM-DD date, 0 = Monday (the schedule grids start their week on Monday). */
export const weekdayOf = (iso) => …
```

## 6. Comentarios de línea (`//`)
- Explican el **porqué**: «el navegador no hereda el PATH de la terminal en macOS», «`rev` evita pisar el cambio de otra persona», «un login falla siempre en el mismo tiempo para no revelar si el usuario existe».
- Marcan **secciones** con `// ---- título ---------------------------------------------`.
- Documentan **trampas** descubiertas con un error real (con el síntoma, no con la anécdota).
- **No** repiten el código, **no** dejan código comentado y **no** llevan fechas ni nombres de personas. Un pendiente se escribe `TODO(motivo): …` y se resuelve o se abre una incidencia; no se acumulan.

## 7. Pruebas
- Cada fichero de `tests/` empieza con una cabecera que dice **qué módulo prueba y qué garantías cubre**.
- El nombre de cada `test(...)` es una **frase que afirma un comportamiento** («an approved budget is locked», no «test budget»).
- Una corrección de un fallo lleva su prueba de regresión, con un comentario si el caso no es evidente.
- El autotest de escritorio (`desktop/selftest.mjs`) documenta cada comprobación en su nombre y deja capturas en `.scratch/` para revisarlas.

## 8. Documentos de `docs/`
| Documento | Contenido | Se actualiza cuando |
|---|---|---|
| [SOFTWARE.md](SOFTWARE.md) | Cómo está hecho: procesos, capas, ciclo de una petición, datos, documentos, agente, seguridad, publicación, pruebas | Cambia la arquitectura o se añade un módulo |
| [ARCHITECTURE.md](ARCHITECTURE.md) | Diseño y seguridad del servicio | Cambia el despliegue o el modelo de confianza |
| [DESKTOP.md](DESKTOP.md) | La app de escritorio: límites, nube, carpetas de proyecto, lo no verificado | Cambia algo específico del escritorio |
| [OPERATIONS.md](OPERATIONS.md) | Despliegue, usuarios, copias, recuperación | Cambia la operación |
| [DATA-MODEL.md](DATA-MODEL.md), [API.md](API.md), [CODE-MAP.md](CODE-MAP.md), [MEMORIAS.md](MEMORIAS.md) | Referencias **generadas** | `npm run docs` |

Reglas de estilo de los documentos: castellano claro; frases cortas; tablas para comparar y listas para pasos; bloques de código con su lenguaje; **enlaces relativos** entre documentos; nada de capturas que caduquen sin necesidad; lo no verificado se dice («no verificado», «límite conocido»).

## 9. Documentación para el agente
Las pautas (`AGENT.md`, `AGENT.desktop.md`) y las **skills** (`skills/*/SKILL.md`) son documentación que **ejecuta** otro programa. Por eso:
- Cada skill empieza con un *frontmatter* (`name`, `description` que dice **cuándo usarla**).
- Dan **órdenes concretas y comprobables** (el comando exacto, qué mirar en el resultado, la lista de comprobación final).
- Obligan a **no inventar cifras**: toda cifra sale de la aplicación o de la persona.
- Cuando cambia una herramienta (`collado-doc`…), se actualizan a la vez su cabecera de uso, la skill y `AGENT.md`; hay pruebas (`agent-guides.test.mjs`) que lo vigilan.

## 10. Generar y comprobar
```bash
npm run docs        # regenera iconos, MEMORIAS.md, API.md, DATA-MODEL.md y CODE-MAP.md
npm test            # falla si falta una cabecera, un comentario de exportación o un documento generado está desfasado
```
`tests/docs-coverage.test.mjs` comprueba:
1. Todo fichero fuente tiene cabecera.
2. Toda exportación (`export function | const | class`) y todo método público de las clases listadas tiene comentario.
3. Los documentos generados coinciden con lo que generaría el código ahora mismo.
4. Toda ruta, informe y acción tiene descripción en `docs/API.md`.

## 11. Lista de comprobación antes de dar un cambio por terminado
- [ ] ¿Cada fichero nuevo tiene cabecera y cada exportación nueva su comentario?
- [ ] ¿Los comentarios explican el porqué, las unidades y los errores?
- [ ] ¿Ejecuté `npm run docs` y confirmé el resultado?
- [ ] ¿Actualicé `SOFTWARE.md`, `DESKTOP.md` u `OPERATIONS.md` si cambió el comportamiento?
- [ ] ¿Los textos de interfaz nuevos están en los tres idiomas?
- [ ] ¿Las pautas del agente reflejan el cambio (si afecta a las herramientas)?
- [ ] ¿Hay una prueba que falle sin el cambio, y su nombre es una frase?
- [ ] `npm test` en verde.
